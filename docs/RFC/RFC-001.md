# RFC-001: Project Execution and Documentation Protocol

## Status

Accepted

## Type

Process / Development Protocol

## Date

2026-07-24

---

# 1. Summary

This RFC defines the development protocol for Saint.

The purpose of this RFC is to establish how significant work should be planned, documented, executed, and reviewed.

The core principle is:

> **Significant changes should be understood and documented before implementation.**

---

# 2. Motivation

Saint is an experimental project involving:

* Agent orchestration
* DataHub context
* LLM integration
* Adaptive paths
* Learning and exploration flows
* Frontend and backend systems

The project is expected to evolve during development.

Without a clear execution protocol, changes may:

* Expand the scope unintentionally
* Conflict with existing architecture
* Create undocumented decisions
* Introduce unnecessary complexity
* Make future development difficult to understand

This RFC establishes a lightweight process for preventing those problems.

---

# 3. Scope of This RFC

This RFC applies to significant work that may affect:

* Product behavior
* Core user flows
* Architecture
* DataHub integration
* LLM integration
* Domain models
* Major frontend structures
* Major backend structures
* Project scope
* Technical direction

Small implementation details do not require a new RFC.

---

# 4. What Counts as a Significant Change?

A change should generally be considered significant if it:

* Introduces a new major capability
* Changes an existing core user flow
* Changes architectural boundaries
* Adds a major external integration
* Changes the role of DataHub
* Changes the role of the LLM
* Introduces a major data model
* Adds a new system subsystem
* Changes the project's core product direction
* Requires substantial changes across multiple components

Examples:

```text
Adding a button
```

Usually does not require an RFC.

```text
Replacing the entire goal-to-path architecture
```

Requires an RFC.

---

# 5. Required Workflow

Significant work should follow:

```text
IDENTIFY
    ↓
UNDERSTAND
    ↓
PROPOSE
    ↓
DOCUMENT
    ↓
REVIEW
    ↓
IMPLEMENT
    ↓
VALIDATE
    ↓
UPDATE DOCUMENTATION
```

---

# 6. Before Implementation

Before implementing significant work, the agent should:

1. Understand the current architecture
2. Inspect relevant project documentation
3. Identify affected components
4. Determine whether the change conflicts with existing decisions
5. Identify potential alternatives
6. Determine whether a new RFC is required

The agent should not begin a major implementation based only on a vague assumption.

---

# 7. RFC Requirement

A new RFC should be created when a significant change:

* Changes architectural direction
* Introduces a major capability
* Creates a new system boundary
* Changes an existing technical decision
* Changes a core product assumption

The new RFC should document:

```text
Problem
    ↓
Context
    ↓
Proposed Change
    ↓
Alternatives
    ↓
Trade-offs
    ↓
Decision
```

---

# 8. Existing Decisions Must Be Respected

Before introducing a significant change, the agent should review:

```text
docs/00-ProductPrinciples.md
docs/01-Vision.md
docs/02-PRD.md
docs/06-Architecture.md
docs/07-TechnicalDecisions.md
docs/08-design.md
docs/09-Roadmap.md
docs/10-Manifesto.md
```

The agent should understand the project's existing direction before proposing changes.

A new implementation should not silently contradict existing decisions.

If a contradiction is necessary, it should be explicitly documented.

---

# 9. Documentation Before Significant Implementation

The project follows this principle:

> **If the scope is large enough to change the direction of the project, the reasoning should exist before the code.**

This does not mean every small implementation detail must be documented.

The goal is to preserve important context without creating unnecessary bureaucracy.

---

# 10. Implementation Protocol

After a significant change has been approved or defined, implementation should proceed in manageable increments.

Preferred workflow:

```text
Small Scope
    ↓
Implement
    ↓
Test
    ↓
Review
    ↓
Continue
```

The agent should avoid implementing a large unverified change across the entire repository in a single step when it can be safely divided into smaller increments.

---

# 11. Validation

Significant work should be validated against its intended outcome.

Validation may include:

* Automated tests
* Manual testing
* Integration testing
* UI verification
* DataHub integration verification
* Agent behavior evaluation
* End-to-end testing

The validation method should match the type of change.

---

# 12. Documentation After Implementation

After significant implementation, relevant documentation should be updated when necessary.

Documentation may include:

* Architecture
* Technical decisions
* Design
* Roadmap
* Changelog
* RFCs

The final implementation should not significantly diverge from the documented decision without updating the documentation.

---

# 13. Change Management

When a change is discovered during implementation, the agent should classify it.

```text
┌──────────────────────────────┐
│        CHANGE DISCOVERED     │
└──────────────┬───────────────┘
               │
       ┌───────┴────────┐
       ▼                ▼
   Minor Change     Significant
       │                │
       ▼                ▼
   Continue       Document / RFC
```

Minor changes may be implemented directly.

Significant changes should be evaluated before implementation continues.

---

# 14. Agent Responsibilities

The agent working on Saint should:

### Understand Before Acting

Inspect the relevant context before modifying the project.

### Preserve Existing Intent

Do not remove or alter important behavior without understanding its purpose.

### Avoid Unnecessary Complexity

Do not introduce architecture merely because it is technically interesting.

### Explain Significant Decisions

Make major changes traceable.

### Keep Changes Focused

Avoid unrelated refactoring during feature implementation.

### Validate Work

Verify that the implementation actually satisfies its intended purpose.

### Update Documentation

Keep important project knowledge synchronized with the implementation.

---

# 15. Anti-Patterns

The following behaviors should be avoided.

## Silent Architecture Changes

Changing major architecture without documentation.

## Scope Expansion

Adding features that were not required by the current task.

## Unrelated Refactoring

Changing unrelated code while implementing a focused feature.

## Premature Abstraction

Creating abstractions before a real need exists.

## Documentation Drift

Allowing the code and documentation to describe different systems.

## Blind Implementation

Writing code without inspecting the current project context.

## Overengineering

Building infrastructure for hypothetical future requirements.

---

# 16. Definition of Done for Significant Work

Significant work is considered complete when:

```text
Requirement
    ↓
Implementation
    ↓
Validation
    ↓
Documentation Review
    ↓
Complete
```

The implementation should:

* Satisfy the intended requirement
* Respect relevant architectural decisions
* Be validated appropriately
* Avoid unnecessary scope expansion
* Have relevant documentation updated

---

# 17. Guiding Principle

> **Think before building. Document before changing direction. Build incrementally. Validate the result. Preserve the reasoning.**

---
